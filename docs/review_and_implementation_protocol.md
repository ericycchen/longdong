# 審查與實作規範

## 目的

消除兩類重複：對下層已保證之事的重複驗證，與對已裁決之事的重複回報。讓每一條檢查、每一筆審查回報都有明確的存在理由。

## 背景

沒有宣告過的權責分界時，每一層各自防範上游本已排除的輸入，檢查數量隨層數相乘而非相加；審查則在沒有可達性判準的情況下枚舉缺陷，把不可達的路徑當成缺陷回報，其修法又是再加一層檢查。

第一節到第七節是通用原則，可直接用於其他專案；只有 1.5 的分派表與 5.7 的外部框架清單屬於本專案。

---

## 一、權責分界

1.1 每一層宣告它對上層的保證。該宣告為封閉列舉。

1.2 上層不得重複驗證下層已宣告保證的性質。

1.3 一個性質只能有一個負責層。兩層都驗等同兩層都不負責。

1.4 一層的保證由該層自己的測試證明，不由使用它的層的測試證明。

1.5 本專案的分派：

| 性質 | 負責層 |
|---|---|
| 路線資料的內容正確（難度、Bolt、拉測、安全評級） | Sheet 的維護者（TOCC 固定點更新計畫）；App 照實顯示，不修正、不推測 |
| Sheet 版面的解讀（欄位、合併儲存格、子列、圖例界線、燈號顏色） | 匯入層 `scripts/lib/parse.ts`、`safety.ts` |
| 路線ID 的產生、不重複、不被手動修改 | Sheet 上的 Apps Script（`apps-script/RouteIds.gs`） |
| 已發布的路線ID 不被改掉、不被大量誤刪 | 匯入層的 ID 檢查（`scripts/lib/ids.ts`） |
| 資料檔（`longdong.json`）的結構合法 | 匯入時的 zod 驗證（`src/data/schema.ts`）；前端信任資料檔，不在執行時重驗 |
| 介面文字中英對應完整 | TypeScript 型別（`en.ts` 以 `zh.ts` 的 key 為型別） |
| 離線快取、資料檔與程式的版本更新 | Service Worker（vite-plugin-pwa／Workbox） |
| 登入、權杖、連線與斷線重連、離線寫入佇列 | Firebase SDK |
| 使用者資料的讀寫權限與欄位驗證 | Realtime Database 規則（`firebase/database.rules.json`）；前端不重做權限判斷 |
| 個人資料在多裝置間的合併語意（較新者為準、刪除標記） | `src/personal/reconcile.ts`、`mergeRecords` |
| 建置、測試、部署、每日同步 | GitHub Actions（`.github/workflows/deploy.yml`） |

1.6 分派表的變更為顯式變更，不得由新增檢查隱含達成。

---

## 二、檢查的成立條件

2.1 一條檢查只有在存在一條由真實入口到達違反狀態的路徑時才成立。真實入口指使用者或上游系統實際調用的介面（例如：Sheet 的內容、使用者在畫面上的操作、資料庫規則允許的寫入），不含測試為製造該狀態而直接調用內部函式。

2.2 該路徑必須具體到能寫成一個會失敗的測試。寫不出來即不新增該檢查。

2.3 下層已保證的性質，上層重驗的唯一正當理由是該保證未被測試證明。此時要修的是下層，不是加上層的檢查。

2.4 檢查放在擁有該性質的層，不放在發現問題的層。

---

## 三、實作的成立條件

3.1 使錯誤狀態不可表示的改動，優先於偵測它的檢查（必填參數、型別區分、結構調整）。

3.2 需要選擇的參數必填。不存在「危險的那一邊是預設值」。

3.3 靜默修復禁止——取絕對值、夾取、補值、回退預設都不可。一個狀態要嘛不可能發生因而不處理，要嘛明確拒絕。
例：匯入遇到讀不懂的 Sheet 版面就停止並說明原因，網站維持上一版資料，不猜測、不跳過。

3.4 修正與它的紅案（修正前會失敗的測試）同次提交。

---

## 四、測試的成立條件

4.1 新增測試前先寫出它要抓的突變。突變存活即該測試無內容，應刪除或重寫。

4.2 測試不得與被測程式碼共用輔助函式。

4.3 一條檢查被移除時必須有測試轉紅。沒有則該檢查是死碼，刪除而非保留。

---

## 五、審查的回報條件

5.1 一筆回報必須指出由真實入口到達的路徑。指不出即不回報。

5.2 同一缺陷只回報一次，不因審查角度不同而重複計入。

5.3 已裁決為不修且理由成立的回報，在該理由失效前不得再次提出。

5.4 不得以「新增一條檢查」作為修法建議，除非同時滿足第二節。

5.5 對下層保證的重驗提議，改報為「該保證缺少測試」並指向下層。

5.6 回報數量無下限。湊足數量的回報違反 5.1。

5.7 外部框架負責的性質（1.5 中歸 Firebase SDK、Service Worker、GitHub Actions 者）不回報為本專案的缺陷，本專案也不為它加防禦——重試、去重、補抓、對它的結果再驗證都屬之。依賴它的行為時，把假設寫明，並以實機操作驗證。

---

## 六、判定順序

遇到疑似缺陷時依序判定，命中即停：

1. 哪一層擁有這個性質？不是本層則轉報該層（5.5）；屬於外部框架的不回報（5.7）。
2. 有沒有由真實入口到達的路徑？沒有則不是缺陷（5.1）。
3. 能否讓該狀態不可表示？能則改結構，不加檢查（3.1）。
4. 以上皆否，才新增檢查，並同次提交紅案（3.4）。

---

## 七、審查與提交的時機

7.1 判準是改動有無決定性自證，不是改動的大小。自證指「輸出該不該變」事前有明確預期，且可逐列驗證。

7.2 輸出不該變而確實逐列未變的改動——重構、相消參數的移除、等價替換——其驗證即審查，直接提交，不另跑審查。
本專案可用的零差異證明：重新匯入後 `public/data/longdong.json` 的 `version` 不變；`npm run build` 前後頁面截圖一致。

7.3 引入新行為或新決策路徑的改動沒有零差異可用，須跑審查。

7.4 探索性調整（例如版面、配色的試做）不逐次提交，只提交留下來的結果。

7.5 **自證訊號在合併的瞬間失效。** 具零差異證明的改動，不得與會改變輸出的改動同批提交：兩者混在一起時，前者的證明消失，後者的歸因也失去對照。

7.6 可達性判定的成本隨 diff 規模上升。批次審查不只較慢，且會因判定成本過高而退化成枚舉，違反 5.1。

---

## 八、影響與風險

8.1 成本：每次新增檢查多一次突變驗證；每筆回報多一次可達性判定。兩者都在既有流程內，不新增工具。

8.2 殘餘風險：可達性判定依賴「真實入口」的界定，而界定本身可能過窄。緩解：入口的變更與分派表同屬顯式變更。

8.3 殘餘風險：本規範降低誤報，同時降低對未知路徑的敏感度。它管的是已知結構內的重複，不取代對新結構的探索。
